>> Observación: con allow-backend presente, error-block-dns NO bloquea el DNS (nslookup resuelve
>> postgres-service.gponceb.svc.cluster.local -> 10.97.136.121; el exit code 1 de nslookup se debe a
>> los dominios de búsqueda NXDOMAIN, no a un bloqueo). Las NetworkPolicies son ADITIVAS (unión OR):
>> una política con "egress: []" no revoca lo que otra política ya permite. El fallo aparece cuando
>> la única política que selecciona al pod es la restrictiva. Se simula eliminando allow-backend:

$ kubectl delete networkpolicy allow-backend
networkpolicy.networking.k8s.io "allow-backend" deleted from gponceb namespace

$ kubectl exec deploy/backend-api -c api -- nslookup -timeout=2 -retry=1 postgres-service 2>&1 | tail -3
;; connection timed out; no servers could be reached

command terminated with exit code 1

$ curl -s -m 10 -o /dev/null -w 'GET http://localhost/api/productos -> HTTP %{http_code}
' http://localhost/api/productos
GET http://localhost/api/productos -> HTTP 000

$ kubectl get pods -l app=backend-api
NAME                           READY   STATUS    RESTARTS   AGE
backend-api-7f8496c7f9-68znx   2/2     Running   0          19m
backend-api-7f8496c7f9-rbtbx   2/2     Running   0          19m

>> Solución: eliminar la política errónea y restaurar allow-backend
$ kubectl delete networkpolicy error-block-dns
networkpolicy.networking.k8s.io "error-block-dns" deleted from gponceb namespace

$ kubectl apply -f mod5-networking/07-backend-networkpolicy.yaml
networkpolicy.networking.k8s.io/allow-backend created

$ kubectl exec deploy/backend-api -c api -- nslookup postgres-service 2>&1 | grep -A1 '^Name'
Name:	postgres-service.gponceb.svc.cluster.local
Address: 10.97.136.121
